# 0002. 单主 VM 加执行上下文隔离的 Agent 沙箱

日期：2026-10-22

## 状态

已采纳 (Accepted)，尚未实现

## 背景与问题

日常习惯是多个 OMP 同时在不同项目运行。每个项目一台 VM 的内存成本过高，管理也更复杂；把整个 `~/Code` 可写挂载给一台 VM，又让 Agent 能误删其他项目

要防的是 Agent 误操作，例如 `rm -rf` 越界、误连其他项目的私网服务，不防恶意 Agent 逃逸内核隔离

microsandbox 0.7.7 的挂载、网络规则和 secret 都在 VM 创建时固定，运行中修改需要重启，会打断同一 VM 内的其他 OMP。获取方式：

```bash
msb modify --help
PROBE=x msb modify --secret PROBE@example.com --dry-run <sandbox>
```

## 决策

1. **一台主 VM 承载所有日常执行上下文**。每次启动 OMP 新建一个执行上下文，同项目可并存多个，启动新上下文不影响已运行的上下文
2. **能力分两层**：
   - 能力上限：主 VM 创建时固定，由全局 YAML 声明。挂载根为 `~/Code`、`~/nix-config`、`~/.herdr/worktrees`，guest 内路径与宿主一致；网络为公网加家庭网段；secret 全局声明
   - 能力授权：启动上下文时由受信任 launcher 在上限内授予。文件系统只绑定当前项目，worktree 自动加绑 git common dir；网络只放行项目声明的目标
3. **项目配置为仓库根 `.sandbox.yaml`**，只包含三类请求：
   - `imports`：宿主文件，启动时复制进上下文，退出删除，不写回宿主
   - `network`：私网目标，必须落在网络上限内
   - `paths`：项目外的额外目录，必须落在挂载根内，默认可写，可逐项声明只读
4. **超出上限时报错**。主 VM 空闲时，下一次启动按新上限重建；主 VM 仍有上下文时记录待升级，不打断它们
5. **OMP 数据、工具和缓存在主 VM 内所有上下文共用一份可写状态**，与宿主多个 OMP 共用一份 XDG 数据的语义一致
6. **附加 VM 只由 `omp-sb --dedicated` 显式创建**。按项目保留一块 disk，同项目的多个上下文进入同一台附加 VM，最后一个上下文退出后删除 VM
7. **入口**：`omp-sb` 启动 OMP；`sb` 替换 `sb-default`，承担 `run`、`shell`、`status`、`up`、`down`、`volume`

## 考虑过的替代方案

- **每个项目或每个 OMP 一台 VM**：并发 4 个时启动后宿主内存约 2.8 至 2.9 GB，比单 VM 多约 1.1 GB，且需要管理多台 VM
- **单活动槽位，切换项目时替换 VM**：会打断其他项目正在运行的 OMP
- **私网项目必须使用附加 VM**：每上下文独立网络命名空间可以在主 VM 内按项目精确放行私网目标，不需要额外 VM
- **guest 内按 UID 过滤网络**：guest 内核缺少 iptables `owner` 匹配模块，无法实现
- **VM 级挂载凭据目录**：新增凭据目录需要重建 VM；运行时复制不需要，并保证宿主文件不被写回
- **项目配置放宿主集中目录**：Agent 无法修改，但新项目需要在另一处登记。上限约束下，Agent 修改仓库内配置最多在上限内扩权，且下次启动才生效

## 影响与代价

- launcher 是唯一的隔离执行者。launcher 缺陷或内核逃逸会暴露整个能力上限，所以上限必须是可接受的最坏情况
- 公网目标只在 VM 级控制，不做上下文级限制；按项目精确控制只覆盖私网目标
- 同一主 VM 内某个上下文耗尽内存时，可能波及其他上下文
- 附加 VM 不能挂载主 VM 的 disk，工具需要在附加 VM 内各自安装一次
- 资源与隔离实测记录见 wiki 页面 `microsandbox-concurrency-resource-cost`
