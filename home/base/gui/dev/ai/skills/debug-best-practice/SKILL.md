## Rules

- 如果还没阅读 `diagnosing-bugs`, 先阅读该技能, 我以下没有提到的点, 这个技能作为兜底要求
- 如果是代码相关, 优先找 代码位置 -> 最近git历史(git仓库) -> 然后看看有没有日志输出, 看最近日志
- 在你需要ctx搜索/网络搜索时, 同时 执行多条命令/调用多个tool 提高效率
- 遇到难点卡住, 先找找官方文档, ctx7 查询, 如果没有, 找网络搜索, 搜索网络相关issue; 如果涉及项目有github仓库, 去github上搜索相关issue(gh)
- 在确定根因后, 依然不能直接依赖自己已有知识, 依然是, 先ctx7看看对应版本的文档, 然后search网络上类似的issue; 推荐对用户来说最简单的方案, 跟用户确认后再执行
- 跟用户反馈时, 必须给出根因的证据, 绝对不能是头疼医头脚疼医脚的表面因素和修复方案; 描述根因时, 如果涉及日志有时间点, 告诉用户当时现场执行了什么导致的; 给出反馈时, 必须写出自己最推荐的方案和理由;
- 一般解决方案的优先级为: 社区常见问题且证明有效优先 -> 不常见且根据根因确定有效解决且具有鲁棒性且最简单 -> 没有推荐, 给出最可行的几个用户自己抉择
- 方案必须预想到可逆情况, 也就是假如方案失败, 能不能回退, 风险应该告知或者帮用户做好处理
- 成功后, 必须清理 临时文件/临时代码, 保证工作整洁, 跟用户确认后清理
- 执行长耗时命令时,禁止无条件等待,使用显示打印 成功/失败 信号的方式和设置合理超时时间;for短时间轮询操作替代无限时等待
- 优先尝试快速且低成本的排查方式
- 遇到网络ip`198`开头的,意味着本地使用tun网络代理,不要在本地进行任何网络相关的测试和验证,跟用户反馈

## DISCOVER.md

**适用于具体项目中**

- 遇到棘手问题时, 先在项目根目录下创建一个 `DISCOVERY.md`; 然后将每次重要发现全部进行记录
- 成功解决且结束后, 沉淀有用的经验(检查项目可能存在的文档目录位置例如 docs/postmortems/.memory 等等目录)然后删除掉DISCOVERY.md,不准进入git
- 文档应该包括但不限于: 已经失败过的尝试/成功的尝试/试错过程犯的错误和经验
- 文档应该包含时间线, 越新越后面; 阅读时应该优先从后往前阅读
- 收尾删除前, 务必检查所有发现, 提取有用的部分, 抛弃流水账的部分, 保留经验教训, 通过阅读`project-memory`skill, 检查哪些值得保留, 寻找需要记录的位置, 如果项目还没有, 向用户提建议, 展示要保存的摘要, 用户同意后, 存入
