# computer-use AX 树遍历饥饿与虚假播放确认

**日期**: 2026-09-04
**影响**: 在使用 `computer-use` 控制 Audirvana 播放曲目时，因 AX 树遍历截断、缺少双击原语以及虚假确认（将列表选中高亮态错误判定为正在播放），导致自动化控制彻底失败且向用户输出了不可信的虚假结论。
**发现人**: shelken

## 问题

用户要求使用 `computer-use` 控制 Audirvana 播放一首歌曲。自动化操作中出现三连击式严重问题：

1. `computer-use snapshot` 抓取的界面中根本没有播放控制条（Play/Pause/进度条），底层超时或报截断；
2. 即使选中了曲目行，应用根本没有开始播放；
3. Agent 未经任何客观状态比对，草率根据列表项高亮态与 `effect: unverifiable` 宣称“已成功播放”，被用户当场批评。

## 根因

1. **AX 树深度优先遍历（DFS）截断饥饿**：
   - Audirvana 等多媒体管理软件包含庞大的 Outline/Table 树（945+ 曲目，成千上万节点）。
   - 默认深度优先遍历（DFS）一旦深入曲目列表容器（Element 6），就会在内部耗尽节点预算（`max_elements`），**无法回溯到同级后续兄弟节点**。
   - 播放控制栏（`AXButton "P"`、`AXSlider` 等）在窗口层级中位于曲目列表之后，因此被完全截断吞噬，导致 Agent 在快照中“盲目”。
2. **缺少双击命令（Double Click）**：
   - 绝大多数桌面音乐播放器和文件列表，单次点击仅为聚焦/选中（`selected: true`），必须**双击**或按 `Space`/`Return` 才会触发播放。
   - 旧版 `computer-use` 仅提供 `click`（单击），无法通过标准交互触发展开或播放。
3. **文本输入原语缺失与 AXPress 报错 -25206**：
   - 搜索框（`AXTextField`）不接受 `AXPress`，硬编码该动作会导致底层报错 `-25206`。
   - 旧版没有封装文本输入命令，无法完成曲目搜索输入。
4. **窗口管理器离屏偏移**：
   - 系统运行平铺窗口管理器（OmniWM），后台工作区窗口被放置在屏幕外（`x: 1919`），导致像素坐标点击失效。
5. **虚假确认与验证机制缺失**：
   - `cua-driver` 在没有值读取时返回 `effect: unverifiable` 属正常现象；但 Agent 将“列表行高亮（`sel`）”直接臆断为“正在播放”，完全违背事实。

## 修复

1. **`computer-use.ts` 架构与命令全面重构**：
   - **防截断策略**：默认遍历深度设为 5，并开放 `--depth <N>` 与 `--query <str>`。对于海量列表窗口，指定 `--depth 3~5` 可在 100ms 内极速返回完整的控制条。
   - **语义描述增强**：从 `tree_markdown` 自动提取 description 与 actions，将单字符按钮（`P`、`S`）转化为直观语义（如 `P (Play/Pause playback)`）。
   - **补齐原语**：新增 `double-click`、`type`（优先走原生 `set_value` 毫秒级直写）、像素坐标自动转窗口本地坐标、AXPress 失败自动降级。
   - **离屏智能修复**：`front` 自动检测并拉回平铺窗口管理器推入屏幕外的窗口。
2. **SKILL.md 写入铁律验证标准**：
   - 严禁将列表项选中态（`sel`）等同于播放；
   - 播放状态必须以进度条数值（`Slider`）发生随时间位移、或通过原生 AppleScript（`osascript -e 'tell application "Audirvana" to get player state'` 返回 `Playing`）为客观铁证。

## 预防

- 凡涉及视音频播放、下载、长时间执行等状态任务，绝不能单凭点击事件的成功返回推定业务结果。必须设计明确的差分验证（前后数值位移、原生状态机读取）。
- 遇到复杂应用 AX 树过大时，第一时间使用 `--depth` 降低遍历深度或使用 `--query` 准确定位，绝不盲目调大元素预算。
- 控制桌面应用前，必须先调用 `front` 确保窗口在屏幕真实可视区域内。
